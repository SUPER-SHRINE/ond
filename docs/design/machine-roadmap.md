# Ondのマシン機能のバージョン計画案

状態: 検討用の非規範計画。作成日: 2026年10月4日。

[操作フロー](machine-workflow.md)の各操作を、利用者が完了できる仕事の単位でリリースへ配分する。仕様書駆動とアプリ・runtimeの独立生成は最初の新版から必須にし、GUI、配布、複数OSへ段階的に広げる。中期の到達点は0.6.0、長期の互換性保証を確立する候補は1.0.0とする。

[デバイス製品形式](device-package.md)の基礎と、通常成果物への必要仕様本文の必須同梱も0.2.0から導入する。0.6.0は仕様が初めて保存される版ではなく、第三者製品の共有と、来歴等を加えた保存物からの復元を完成させる版とする。

[組立境界](device-assembly.md)で定めるhost接続profileも、0.2.0から公式の最小実装で評価する。製品を包装できることと、そのbinaryを既成runnerへ接続できることを別に検証する。

0.1.2でこの文書群を公表し、その後に0.2.0の開発へ進む。0.2.0以降の版番号は機能配分の提案であり、公開日や工数の約束ではない。規範仕様や公開APIの変更もこの文書だけで確定しない。期間は0.2.0の試作から作業量を把握した後に見積もる。

## 現在の出発点

[0.1.0のリリース記録](../releases/0.1.0-notes.md)から続く0.1系列を出発点とする。compiler-core、Kagura backend、Object／LinkedImage、`compile`／`link`、LSPがあり、[README](../../README.md)と[0.1.1のリリースノート](../releases/0.1.1-notes.md)ではWindows x64とLinux x86_64（glibc）を検証・配布対象としている。machine構成、起動、asset処理、実行環境はSDKの責務であり、今回の統合フローは未実装である。各版の公開状態は[変更履歴](../../CHANGELOG.md)とリリース記録を参照し、この設計書で公開済みとは推定しない。

既存compiler・CLI・LSPの対応OSと、新しいmachine runtimeの対応OSは別の範囲である。0.2.0の最小runtimeをWindowsから始め、0.5.0で複数OSへ広げる計画は、既存compilerのLinux対応を取り消したり先送りしたりする意味ではない。

0.1系列の標準経路の再現性と重大な不具合修正という方針を維持する。0.2.0以降の案は、それぞれ既存のコンパイル経路も維持する。公開済みのREADMEにある0.2.0までの安定性説明と、以後の試験的なmachine形式の扱いは、0.2.0公開前に明示的に整合させる。

| 0.2.0 | 一台のマシン用に書き、CLIで動かせる | 製品形式の基礎、仕様必須同梱、machine定義、SDK、独立build、最小runner、snapshot | 固定画像を表示し、同じアプリを第二のdevice実装でも動かす |
| 0.3.0 | GUIで組み替え、動作中の中身を見られる | ボード編集、入力とaudio、VRAM・波形、変更反映 | 入力で図形を動かし、音を鳴らし、内部を同時観測する |
| 0.4.0 | Windowsの別の人へ作品と設計資料を渡せる | asset処理、一括配布、launcher、仕様の閲覧、受取側の診断 | 開発ツールのないWindowsで配布物を起動し、同梱仕様をオフラインで読む |

| 0.6.0 | 部品を共有し、Enbuを構成し、作品と来歴を保存できる | 外部device製品の受渡し、Enbu統合、拡張保存、復元試験 | 製品から作品への共有の連鎖と、元配布元・runtimeなしでの復元を実演 |
| 1.0.0候補 | 公表された互換範囲で長く使える | 安定した保存契約、互換表、移行手段、回帰資産 | 保存済みの標準sampleが対応表どおり継続実行できる |

各版の機能IDは[フローから得た機能一覧](machine-workflow.md#フローから得た機能一覧)を参照する。後続の版は、それ以前の操作を回帰させないことを前提とする。

## 0.1.2で公表する範囲

この計画から0.1.2へ持ち込むのは、[文書の入口](README.md)と、全体設計、操作フロー、版計画、device製品形式、組立境界の五つの文書である。既存機能の保守とは区別し、machine/deviceコマンド、GUI、新runtimeや新ABIの実装をこの文書収録の条件にはしない。

リリース作業では次を確認する。

- READMEとリリースノートから設計文書へ案内し、未実装の提案であることを明記する。
- WindowsのZIPとLinuxのtar.gzへ`docs/design/`一式を含め、展開後に入口と五文書を開けることを検査する。ソースarchiveだけへの収録を、binary配布物への同梱と混同しない。
- 文書間の相対リンクを保持する。規範仕様やソース等のrepository資料へのリンクは、同梱される範囲とソースcheckoutで参照する範囲を文書の入口で区別する。
- バージョン情報、変更履歴、releaseノート、配布物の検証はリリース担当の工程で行う。文書を追加しただけで公開完了と扱わない。

0.1.2公開後は新機能開発の主対象を0.2.0へ移し、まず下記のゲートAへ進む。最小graphicsの動作・window、machineの時間・起動、host接続の操作とbuffer寿命、成果物wrapperを具体化し、独立実装と接続試作で検証する。ロードマップの公表を、具体的なABIや依存追加まで承認済みとみなさない。0.1系列に必要な保守は、新機能開発と分けて扱う。

## 0.2.0の範囲と終了条件

F01〜F09、F19、F20と、F10のsnapshot、F16の本文同梱と依存検査、F18のversion記録を導入する。固定された小さなKagura machineから始め、RAMと最小graphics、起動・終了の契約を仕様化する。CLIではmapの読込・検証・変更ができるが、任意device向けのGUIはまだ提供しない。

同じ版の中を、次の実装ゲートへ分ける。AからCは内部の作業単位であり、別の公開versionではない。

| ゲート | 成果 | 終了条件 |
| --- | --- | --- |
| A 仕様を独立に実装する | 最小device・machine・load・時間・観測の規範仕様案、共通適合試験、第二実装 | 元実装を見ずに仕様を実装でき、正常系・境界値・fault・resetの試験が通る。時刻に関わる機能は順序も検査 |
| B 二つの成果物を作る | machine読込と検証、SDK生成、アプリwrapper、Windows runtime | host binaryのない環境でアプリをbuildでき、アプリsourceとimageを与えずにruntimeを用意できる |
| C 普段の開発を一周する | project作成、LSP連携、build/run、snapshot、診断、チュートリアル | 最初の固定画像を表示でき、MMIO変更後も同じsourceで再buildできる。別実装で未変更のアプリ成果物が動く |

アプリ/runtimeの不適合な組合せはguest実行前に拒否する。観測ON/OFFで規定動作が変わらないこと、compilerとLSPが同じSDK世代を読むこと、古い生成物を新しい構成として起動しないことをリリース条件にする。独立実装による検証は、同じcoreを別OS向けにcompileしただけの二実装では代用しない。

同梱deviceにも製品manifestを適用し、仕様一式と一つ以上のhost実装、内容目録、配布条件を表現する。製品を読むだけではnative codeをloadしない。製品としての最小構成と、独立実装検証等の品質判定を分ける。

アプリとruntimeを別々に持ち出しても、必要なmachine定義と規範仕様本文をオフラインで読めることを検査する。本文の参照依存を閉じ、欠落と改変を検出して最終生成を止める。host binaryの入手をアプリbuildの前提にしない。中間Objectや既存LinkedImageへの本文埋込みではなく、新しい成果物wrapperで扱う。

同じruntimeで第二のアプリも動かし、同じ種類のdeviceを二つ持つ構成を検証して、アプリや`gpu0`一個に依存した設計を残さない。最小graphicsの範囲で試験し、多種類のdevice追加をこの版の条件にはしない。

ゲートAからBで一種類のhost接続profileを試し、既成runnerとnative module方式の採否を判断する。採用条件は、同じrunner binaryへ独立した二実装を接続でき、device作者のsourceや利用者のnative toolchainを要求しないこととする。複数windowが同じinstanceを参照すること、instance間の状態分離、未知profileの拒否、失敗時の解放、信頼前にloadしないことを検査する。静的収録だけの試作へ縮小する場合は、その制限と後続への影響を明示し、個別binaryの組立が実証済みとはしない。

GUIの完成、audio、外部asset変換、一般利用者向け一括配布、三つのOSはこの版の完了条件にしない。ただし後続で必要な仕様・成果物の識別、host条件、観測schemaを表現できる境界を確認する。

## 0.3.0の範囲と終了条件

F11と、F10のlive購読・標準viewを導入する。最小のCommonInputとCommonAudio、入力loop・frame待機・PCM送信を行うguest SDKを加える。新deviceも仕様と適合試験を先に用意し、独立実装で検証してから正式な対応範囲へ入れる。

ボードでdeviceを追加し、windowをmapし、競合を修正し、save・再読込して同じmachineを得られることを条件にする。表示名・座標とinstance ID・論理接続を区別し、undo/redoとAPIへの影響表示を提供する。GUIの保存結果とCLI検証は一致させる。

部品詳細で製品・仕様・実装の識別と対応先を確認し、同梱仕様書を開ける。現在のOSで実装を動かせなくても、資料の閲覧は可能にする。

入力で図形を動かし音を鳴らすsampleを、VRAMと波形を同時に開いて実行する。pause時は同じepochの状態を読み、観測更新が追い付かない場合は古さを示す。構成編集からSDK再生成、LSP再診断、再build、再起動までを通す。

入力のフォーカス喪失とresetを試験し、音声は「PCMが生成されない」と「生成されるがhost出力が使えない」を区別できることも実演する。

汎用GUIの方式や配布単位は着手前に比較し、選択理由を残す。3D表示、電気回路simulation、hot-plug、任意の独自UI pluginはこの版に含めない。

## 0.4.0の範囲と終了条件

F12とF13を導入し、Windowsの受取側が開発環境なしで遊べる状態にする。外部画像・音声の最小の対応形式を選び、変換設定、asset ID、内容hashを固定できるようにする。変換の規則は規範資料に記し、長期保存時には実行に必要な変換済みの資源も残す。

独立したアプリとruntimeを入力に、一括配布物とlauncherを生成する。アプリ成果物の内容を変えずに包装し、そこから取り出したアプリを別runtimeへ渡せることを確認する。開発用の絶対pathや生成SDK、Rust、Ond compilerが受取側に必要でないことを検査する。

保存用optionを指定しない通常の配布物にも必要仕様本文・索引・配布条件を含め、受取側がネットワークなしで読めることを検査する。包装の重複排除で、取り出したアプリ単体の仕様本文が欠落しないことも確認する。

受取側のWindowsで、初回起動、資源不足、不適合runtime、破損した成果物の診断を確認する。対応最小OSやsystem library等の実行前提を明記する。installer、自動更新、公開registryは後続の判断とする。

## 0.5.0の範囲と終了条件

F14を導入する。候補となる正式検証先はWindows x64、macOS arm64、Linux x64の一つの明示した配布環境とし、最小OS、CPU、必要libraryを着手時に確定する。対応環境とdevice実装の有無を一覧で確認でき、runtime解決がOSとCPUの条件から適切なartifactを選ぶようにする。

同じmachineと同じアプリ成果物の内容hashを維持したまま、各hostで起動する。同じ初期状態と入力列について、規定時刻のguest状態、画素、生成PCMを比較する。window表示や物理audio出力も各実環境で確認し、headless試験だけで正式対応とはしない。

署名や包装で対象OSの作業環境が必要な場合は、その工程を明記する。「どのOSからでも他の全OSの配布物を完結して作れる」は追加要件として扱う。検証hostは0.2.0から確保を進め、0.5.0直前に初めて移植性を調べる計画にはしない。

## 0.6.0の範囲と終了条件

F15とF17、F16の拡張保存と復元を導入する。第三者が仕様一式と一つのhost実装から製品を包装・受渡しできるようにし、受取側が提供元、対応契約、host条件、内容hash、配布条件、適合根拠の有無を確認してローカル登録できるようにする。導入時の信頼モデルとhost接続方式は、一般の外部binaryを扱う前に確定する。形式検査・登録とbinaryの実行有効化を分ける。公開registryは完成条件にしない。

外部製品はrunnerが対応する接続profileのものを対象とする。OSと動作仕様が合うだけで任意binaryをloadしない。`build-runtime`で包装し、利用者のnative linkなしに接続できることを確認する。別processやWasm等すべての接続方式の完成は要求しないが、採用方式の信頼と隔離の限界は明示する。

Enbuの現行device、banking、boot、assets、cartridge要件を事前調査し、共通モデルで表せる範囲と不足を記録する。Enbu sampleを通常のmachine・device・包装adapter経由でbuildし、compilerへのEnbu名による分岐を必要にしないことを確かめる。必要なEnbu側の変更は別repositoryの作業として管理する。

保存用exportでは、通常成果物に必須の規範仕様一式、boot資源、アプリ、assetsに、試験、設計理由、変更履歴、由来等を追加する。ネットワークと元のnative runtimeに依存しない環境で、別実装を明示的に登録して同じアプリを起動する。仕様から独立実装を作る検証と通常成果物への本文同梱は0.2.0から継続し、この版では保存物全体からの復元を完成させる。

「作者が製品を渡し、利用者が作品を作って配り、元の配布元消失後も受取側が通常配布物から仕様を読める」という連鎖を実演する。異なる作品の同一仕様から、digestで照合して欠落fileを補う試験も行う。同じID・revisionの異なる本文は競合として保持し、コピー数で上書きしない。

## 1.0.0を判断する条件

F18の互換性方針を確立する。少なくとも、標準machineとdeviceの規範仕様、device製品・仕様目録・アプリ・保存物の読込形式、必要なruntime契約について、何を保証し、対応外になった場合にどう移行するかを明示する。内部MIRやすべてのRust APIを同時に恒久固定する意味ではなく、保証対象ごとに判断する。

独立した別実装、対応OSでの検証、保存物からの復元、既存sampleの回帰試験が継続して通ることを条件にする。正式な互換範囲を試験結果と公開資料に結び付け、今後の実装差替えでもアプリ成果物を保持できる状態を目指す。

## バージョンの軸を混ぜない

| 対象 | 識別するもの | 更新時の扱い |
| --- | --- | --- |
| Ondのリリース版 | 利用者に提供するtoolchainの機能集合 | この文書の0.2.0等。device仕様の版とは連動しない |
| Deviceとmachineの仕様revision | guestから見える動作、時間、配置等の契約 | 公開済み本文を保持し、訂正と互換性への影響を明記 |
| Device製品のrelease | 仕様と実装を包装した製品の版 | 実装追加で製品を更新しても、変更していない仕様revisionとdigestは保持 |
| 成果物のformat version | device製品、仕様目録、app、runtime、machine、保存物を読み取るための形式 | 対応表と必要な移行手段を持つ |
| host接続APIのversion | runtimeとdevice実装の接続方法 | アプリの論理互換性とは分ける |
| 実装versionと内容hash | どのrunner・device・SDK・生成器を使用したか | buildの再現記録に残し、実行契約とは区別 |

0.2.0以前から存在するKaguraやOndの仕様versionを、この計画の都合で振り直さない。新仕様の試験中revisionは固定して記録するが、安定した仕様への昇格は独立実装と適合検証を通して判断する。

0.xの新しいmachine形式も、破壊的変更を黙って適用しない。公開する版ごとに対応する形式を示し、旧成果物を受け付けない場合は理由を診断する。必要な変換は明示操作にし、元の保存物を保持する。現行の公開方針への変更が必要なら、リリース前に具体的な互換方針として承認・文書化する。

## 着手順と外部依存

最初の実装作業は0.2.0のゲートAである。Device Contract、Machine Definition、Inspection Schema、アプリwrapperの最小例をまとめ、独立実装で仕様の不足を洗い出す。ゲートBでは既存compile/linkをつなぎ、ゲートCではクリーンな環境からproject作成・SDK生成・編集・実行を一周させる。

| 先に解決する事項 | 必要になる版 | 扱い |
| --- | --- | --- |
| SDKの永続previewとLSP世代更新 | 0.2.0 | 現行の一時directory運用・変更通知との整合を設計 |
| artifact wrapper、起動・終了・時間契約 | 0.2.0 | 具体的な仕様案と適合試験を用意 |
| device製品形式と規範本文の同梱規則 | 0.2.0 | 最小製品、仕様依存の閉包、目録とdigest、配布条件、破損fixtureを設計 |
| host接続profileと組立計画 | 0.2.0 | 公式の最小deviceでmodule交換、複数window、寿命、資源解放を試作して採否を判断 |
| GUI方式とruntime観測の接続 | 0.3.0 | UIとguest時間を分離した試作で評価 |
| 配布先OSの検証環境 | 0.5.0 | 0.2.0から準備し、実機検証できるまで正式対応を主張しない |
| Enbuの現行仕様との適合 | 0.6.0 | 0.2.0の設計時から不足調査。必要な隣接repositoryの変更は別作業 |

既存の言語仕様、ABI、MIR、Object／LinkedImage、公開API、依存関係に及ぶ実装判断は、具体的な変更案で承認を得て進める。本計画で隣接repositoryを変更しない。Kagura側の変更が必要と判明した課題はリポジトリ方針に従ってblockedとして記録し、解決前に依存する版を完了扱いにしない。

各版では対応する操作フローの実演と適合試験をリリース判定に使う。通常の変更の完了時にはリポジトリのFull品質検査も実行するが、それだけで未実装のmachine機能や新OS対応を検証したとは扱わない。
