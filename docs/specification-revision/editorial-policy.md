# 仕様書の編集方針

この文書群は仕様書再編の決裁と照合を記録する非規範資料である。\
規範の定義元は[移行後の仕様入口](../../specs/README.md)で案内する。\
編集原則とcrate内詳細実装をRust/Ond sourceへ集約する方針は、2026-10-20の会話で採用済みである。\
個別の配置と意味判断は[未決定事項一覧](./open-questions.md)で管理し、本移行の旧新対応は[照合記録](./migration-record.md)で追跡する。

基準資料は Ond repository の commit `06e87c39d99f2389af163d0394d9808f2c3078bd` にある文書とする。\
対象範囲は `specs/` の言語仕様・Kagura target・build関連仕様、および compiler内部契約・適合資料の今回棚卸し分である。\
棚卸し対象はこの範囲の文書とし、具体的な対象は[目次・移行表](./migration-map.md)に列挙する。

関連する検討資料は [目次・移行表](./migration-map.md)、[未決定事項一覧](./open-questions.md)、[整数演算と定数評価の改稿見本](./integer-arithmetic-sample.md) にまとめる。\
目次と移行表は各文書の具体的な移行先を示す。

## 編集の原則

- 各規範主題は単一の定義元で定義し、関連文書は要約と参照を担う
- 規範要件、解説、適合要件、設計判断の理由はそれぞれの責務を明示する
- 構文を扱う節は文法、成立条件、意味、失敗条件と結果、target委譲を記載する
- 規則が生む保証と未決定の判断は分けて記し、実行動作と実装裁量は明示的な規則で定める
- 外部規範は名称・版・発行物を固定し、参照する規則を特定する
- target固有の契約は適用するtarget名と版を明記した定義元で記す
- 規範文書は外部から観測できる契約を定め、compilerの実装詳細はRust/Ondソースを管理元とする
- 成果物形式版、言語版、ABI版、target profile版、compiler実装版を独立した識別軸として記す

## 機能集合と肯定定義

仕様の機能集合は、本文で明示された構文、型、演算、動作、適合条件と、それらの規則から導出される機能の集合として定義する。\
この集合が当該版の仕様で提供される機能の全体を表す。

各規範文は、成立する入力と前提、成立条件、意味と観測結果、条件不成立時のcompile/link errorまたはruntime fault、targetへ委譲する規則を肯定形で記す。\
たとえば「整数定数式は数学的な正確値で計算する」「配列とstructの代入および引数渡しは値copyする」のように、成立する機能と結果を直接定義する。

短絡評価は、左辺値、値評価対象、式の結果を対応づけて記す。

| 演算子 | 左辺値 | 値評価対象 | 結果 |
| --- | --- | --- | --- |
| `&&` | `false` | 左辺 | `false` |
| `&&` | `true` | 左辺、右辺 | 右辺値 |
| `||` | `true` | 左辺 | `true` |
| `||` | `false` | 左辺、右辺 | 右辺値 |

各経路で行う名前解決、型検査、値評価、範囲検査をそれぞれ明記する。

## 規範節の共通書式

主題ごとの規範節は、必要な項目を次の順で記載する。\
各項目は有効な入力、前提、成立条件と、意味または観測結果を結び付けて説明する。

1. **適用範囲** — 対象の言語版・target・成果物と前提条件
2. **構文** — EBNFまたはsignature、成立する入力形式
3. **静的制約** — 型、名前解決、範囲、宣言位置などの成立条件
4. **意味** — 評価順、結果、観測可能な動作、実装に許される自由
5. **異常時** — 条件不成立時のcompile/link error、runtime fault、trapとその結果
6. **委譲** — targetや外部仕様の参照版、委譲する規則
7. **例** — 成立する入力、期待値、fault、対象型

解説と設計理由は規範文面と区分し、定義元を持つ規則は一箇所だけに置く。\
例は規範本文で定義した入力と意味を示し、適合期待値は仕様から導出して実装評価結果を写さずに定める。

`ond-spec-id`は既存の主題を保って維持し、節の移動や見出し変更後も追跡する。\
新しい主題には一意のIDを追加する。\
機械的な適合要件IDはチェックリスト内で管理し、定義元の規範節への参照として使う。\
適合テストの期待値は仕様から導出し、実装の評価結果を写さずに記述する。

## 判断と移行のゲート

既存の規範的意味を変更する判断は、具体的な根拠と影響を示してユーザーの決裁を得る。\
単なる編集上の移動・言い換えも、その操作が規範の意味を変えないことを照合する。

本移行へ着手する前に、[未決定事項一覧](./open-questions.md)の全項目を根拠とユーザー承認などの明示的な判断で解決し、未解決を0件にする。\
各論点は採用規則または保証範囲、判断根拠、ユーザー承認を記録した時点でresolvedとする。\
具体的な採用規則または保証範囲が確定するまで、その論点をopenとして管理する。\
2026-10-20時点で全9項目の決裁が完了し、本移行着手の判断ゲートを通過した。

移行後の新しい規範文書を採用する前に、意味を維持する移行部分は旧新対応を照合し、承認済みの保証変更は[未決定事項一覧](./open-questions.md)の決裁内容へ対応づけて検証する。\
本文、要件ID、仕様から導出した期待値を照合し、重複定義と決裁範囲外の保証変更がないことを確かめる。\
この採用完了の照合は移行着手前の未決定解決とは別のゲートとする。

## 移行後の読み分け

- `specs/ond/language/v1/`はsource languageの規範
- `specs/ond/targets/kagura-v1/`はmachineとABIの規範
- `specs/ond/artifacts.md`、`linking.md`、`build/`、`debug-metadata/`は成果物と利用境界の規範
- `specs/ond/conformance/requirements.md`と`cases/`は要件ID、規範定義元、入力と期待値の索引
- Rust/Ond sourceはcompiler内部表現、phase、helper、validator、allocator方式の管理元
- `docs/decisions/`は承認済み判断の理由、ここにある移行資料は基準commitと移行後の照合記録

SPEC-Q01〜Q09はresolvedであり、本文移行とID・適合データの対応づけは[本移行記録](./migration-record.md)にまとめた。
